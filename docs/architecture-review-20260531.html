5 exports

Problem

16 server action functions repeat the identical try/catch → {success, error} pattern. Interface is as wide as implementation — each action wraps exactly one API function. Error mapping is scattered across the wrapper layer.

Solution

Extract a single wrapAction<T>() helper. Server action files become thin re-export adapters. Error mapping, logging, and result coercion concentrate in the helper.

Wins

  • locality: error mapping concentrates in one module
  • leverage: one interface, 16 call sites
  • interface shrinks from 16 functions to 1 + 16 one-liner adapters
  • tests hit one wrapAction, not 16 wrappers
  • passes deletion test: delete it, complexity reappears 16 times

Problem

Two modules at 220 lines each with ~80% identical implementation. StatusTabs, badgeClasses, formatCurrency, NoImage, and pagination are duplicated verbatim. Only the API call and column label differ.

Solution

Extract a shared OrderList module parameterized by role. Each page component becomes a thin adapter that passes the role prop.

Wins

  • locality: status badge logic lives in one module, not two mirrors
  • two adapters justify the seam — buyer and seller are real variants
  • interface: one role param replaces 220 lines of duplicated surface
  • ~440 lines collapse to ~230 + two 3-line adapters
  • tests hit the shared module once, role-specific cases parametrized
  • passes deletion test: delete it, status logic reappears in every list

Problem

The 281-line API client is uncoupled from components but tightly coupled to next/headers cookies. Token refresh, retry-on-401, and error mapping have zero tests because they can only execute in a Next.js server context. This is the most critical module in the app.

Solution

Introduce a TokenStore interface (getToken(), setToken(), clearToken()). Production adapter wraps next/headers cookies. Test adapter uses an in-memory Map. The full refresh/retry flow becomes testable in jsdom.

Wins

  • test surface = interface: refresh/retry logic now has a seam for tests
  • two adapters justify the seam — production cookies, test memory
  • locality: token management behavior concentrates behind a small interface
  • remove "can't test critical path" excuse from architecture
  • ~281 lines gains its first test coverage

Problem

Server component pages call apiFetch() directly; client components go through server actions + TanStack Query. Two strategies for the same goal — every new page author must decide which path to take. The server action wrapper layer only exists because client components need it.

Solution

Pick one strategy. Either all data flows through server actions (making them the single seam between UI and API), or server components call the API directly and client mutations use callbacks. Document the chosen approach. This is speculative because both patterns have legitimate use cases in Next.js 16.

Wins

  • one mental model for data fetching — no decision per page
  • server actions become the single seam between UI and API
  • simpler onboarding for new contributors

Top recommendation

Collapse the server action wrapper layer

Highest impact-to-effort ratio. A single wrapAction helper removes 16 identical try/catch blocks without changing any caller. The interface shrinks from 16 functions to 1. Tests hit one module instead of 16 wrappers. This also makes candidate 4 (API client seam) cheaper, since error mapping no longer lives scattered across actions. Start here, then tackle the purchase/sales consolidation (candidate 2).
